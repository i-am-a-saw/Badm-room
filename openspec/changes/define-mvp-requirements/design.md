# Design

## Context

Мотивация и объём — в `proposal.md`, требования и критерии приёмки — в `specs/*/spec.md`.

Текущее состояние кода — шаблон Kotlin Multiplatform без бизнес-логики:
- `server/` — Ktor 3.6 (Netty) с одним маршрутом `/`;
- `core/` — KMP-модуль (android, ios, jvm, js, wasmJs), подключён и к серверу, и к клиенту;
- `app/shared` — Compose Multiplatform UI для android, ios, js, wasmJs; `app/androidApp`, `app/iosApp`, `app/webApp` — точки входа.

Ограничения, влияющие на подход:
- Правила с временными границами (T−2,5 ч, окно отметки 24 ч, списание за 15 мин) должны проверяться автоматическими тестами без ожидания реального времени.
- Вместимость и пересечения должны соблюдаться при одновременных запросах (BKG-03, BKG-05, TTB-05).
- Автоотмена и списание происходят без участия пользователя, переживают перезапуск сервера и выполняются ровно один раз (TTB-16, PAY-04).
- Работа ведётся как дипломный проект: нужна трассировка «требование → код → тест» по ID требований.

## Goals / Non-Goals

**Goals:**
- Сервер — единственный источник истины: все правила из спецификаций проверяются на сервере, клиенты только отображают и подсказывают.
- Доменные правила (статусы, переходы, временные границы) — чистые функции в `core`, покрываемые unit-тестами без БД и сети.
- Каждый сценарий спецификаций становится автоматическим приёмочным тестом на уровне HTTP API.
- Платёжный провайдер заменяем; в MVP работает собственная sandbox-реализация.

**Non-Goals:**
- Реальный платёжный провайдер и движение реальных денег.
- Push-уведомления, WebSocket и обновления в реальном времени: достаточно опроса.
- Ручная рассылка уведомлений администратором (use case «Отправка уведомлений» из `Roles.drawio`) и вся статистика.
- Офлайн-режим клиентов, несколько клубов и часовых поясов, локализация интерфейса кроме русского.
- Desktop-клиент.

## Decisions

### D1. Тонкие клиенты + Ktor-сервер + PostgreSQL
Клиенты Compose Multiplatform (Android, iOS, Web на wasmJs с js-фолбэком) обращаются к REST/JSON API на Ktor; данные хранятся в PostgreSQL.
- *Почему*: атомарная проверка вместимости, фоновые задачи и платежи требуют собственного сервера с транзакционной БД. Шаблон уже содержит Ktor.
- *Альтернативы*: BaaS (Firebase/Supabase) — правила вместимости и задачи по времени пришлось бы разносить по триггерам и функциям, хуже для трассировки и тестов; SQLite — нет блокировок строк и exclusion-ограничений, нужных для конкурентных проверок.

### D2. `core` — общая доменная модель, DTO и чистые правила
В `core/commonMain`: перечисления статусов (неделя, тренировка, запись, оплата, посещаемость), справочник типов TRN-01, DTO API (kotlinx.serialization), функции правил — например «можно ли отменить запись в момент now», «вычислить статус после переноса», «окно отметки посещаемости». Сервер применяет правила как окончательные, клиент — для подсказок вроде «отменить можно до 16:29».
- *Альтернатива*: дублировать правила на сервере и в клиенте — риск расхождений.

### D3. Время: UTC в БД, часовой пояс клуба в конфигурации, внедряемые часы
Моменты хранятся как `timestamptz`; границы недели и отображение считаются в часовом поясе клуба из конфигурации (kotlinx-datetime). Везде, где нужно «сейчас», используется внедряемый `Clock`; в тестах — управляемые часы.
- *Почему*: TTB-01 требует единый пояс клуба; тесты TTB-16, BKG-06, ATT-01 и PAY-04 сдвигают время, а не ждут.

### D4. Конкурентность обеспечивает БД
- **Вместимость (BKG-03)**: запись создаётся в транзакции с `SELECT … FOR UPDATE` строки тренировки, затем считаются активные записи и записи, ожидающие блокировки (D7).
- **Одна активная запись (BKG-04)**: частичный уникальный индекс `(athlete_id, session_id) WHERE status = 'ACTIVE'`.
- **Пересечения спортсмена (BKG-05)**: в той же транзакции блокируется строка спортсмена (`FOR UPDATE`), затем проверяются пересечения.
- **Пересечения тренера (TTB-05)**: exclusion-ограничение PostgreSQL по `(coach_id, tstzrange(start, end, '[)'))` для неотменённых тренировок (`btree_gist`). Полуоткрытый интервал даёт «встык — не пересечение».
- *Альтернатива*: проверки только в коде приложения — гонки при параллельных запросах; оптимистичные версии — больше повторов при пиковой записи на популярную тренировку.

### D5. Доступ к данным и миграции
Exposed (DSL) для запросов, Flyway для миграций схемы; первая миграция создаёт всю схему MVP и справочник типов.
- *Альтернативы*: JDBI или чистый JDBC — больше ручного кода; Hibernate — тяжёл для Ktor и хуже сочетается с явными блокировками.

### D6. Аутентификация: непрозрачные токены сессий в БД
Пароли хешируются Argon2id (или bcrypt, если Argon2 недоступен). При входе выдаётся случайный токен сессии; в БД хранится его хеш. Каждый запрос проверяет токен, роль и флаг блокировки.
- *Почему*: ACL-05 требует, чтобы следующий запрос заблокированного пользователя отклонялся — удаление его сессий в БД даёт это сразу. Смена роли (ACL-04) тоже действует со следующего запроса.
- *Альтернатива*: JWT — блокировка срабатывала бы только после истечения токена или потребовала бы список отзыва.
- Восстановление пароля (ACC-04): одноразовый токен с хешем в БД и сроком 1 ч; письма уходят через интерфейс `Mailer` (SMTP в эксплуатации, запись в лог при разработке и в тестах).

### D7. Платежи: интерфейс провайдера + собственный sandbox
Сервер работает с провайдером через интерфейс с операциями: начать блокировку (hosted-страница провайдера), списать, снять блокировку, создать и деактивировать ссылку на оплату, получить статус; подтверждения приходят вебхуком.
- **Ход блокировки**: при выборе блокировки сервер создаёт запись во внутреннем состоянии «Ожидает блокировки». Она занимает место, но не считается активной и не учитывается в TTB-16. Клиент открывает страницу провайдера; при подтверждении запись становится «Активна» со статусом оплаты «Средства заблокированы», при отказе или по истечении 10 мин удаляется (PAY-03). Данные карты не проходят через наш сервер.
- **Sandbox (PAY-12)**: реализация внутри сервера с простой платёжной страницей и тестовыми номерами карт, задающими исход (успех, отказ блокировки, отказ списания, истечение блокировки). Детерминирован для приёмочных тестов и не требует внешнего аккаунта.
- **Идемпотентность**: у каждой операции уникальный идентификатор у провайдера; переходы статусов выполняются условным обновлением (`… WHERE payment_status = 'HELD'`), повторные вебхуки ничего не меняют (PAY-07).
- **Цена (PAY-01)**: хранится у тренировки в копейках и по умолчанию берётся из таблицы цен по типам; запись хранит снимок цены. Как задаются цены, решится позже — меняется только источник значения по умолчанию.
- *Альтернатива*: сразу подключить тестовый режим реального провайдера — внешняя зависимость в тестах, недетерминированные исходы, нужен договор; останется как будущий адаптер.

### D8. Фоновые задачи: опрос БД в процессе сервера
Корутина в сервере каждые 30 с выполняет идемпотентные шаги:
1. тренировки «Запланирована», у которых `start − 2,5 ч ≤ now`, → проверка минимума (TTB-16);
2. тренировки «Подтверждена», у которых `end ≤ now`, → «Завершена» (TTB-17);
3. активные записи завершённых тренировок со статусом «Средства заблокированы» → списание (PAY-04, PAY-05);
4. записи «Ожидает блокировки» старше 10 мин → удаление;
5. сверка с провайдером платежей, по которым долго нет вебхука.

Каждый шаг — условное обновление в транзакции (`FOR UPDATE SKIP LOCKED`), поэтому пропущенные во время простоя события догоняются после перезапуска, а повторов нет.
- *Альтернативы*: Quartz или внешний cron — лишняя инфраструктура; таймер на каждую тренировку в памяти — теряется при перезапуске.

### D9. Уведомления пишутся в той же транзакции, что и событие
Строки уведомлений (NTF-02…05) создаются в транзакции, меняющей тренировку или оплату. Поэтому уведомление есть тогда и только тогда, когда событие произошло, а повторный запуск задачи (TTB-16) не дублирует уведомления. Клиент опрашивает счётчик непрочитанных раз в 30 с и при открытии экрана (NTF-01: не позже 1 мин).
- *Альтернатива*: очередь сообщений или WebSocket — избыточно без push и реального времени.

### D10. Клиент: общий UI в `app/shared`
Навигация по ролям (гость, спортсмен, тренер, администратор), ViewModel на экран, Ktor Client с общими DTO из `core`. Токен хранится в защищённом хранилище платформы (Keystore, Keychain), в Web — в `localStorage`.

### D11. Трассировка и приёмочные тесты
- Приёмочные тесты — на уровне HTTP API: Ktor `testApplication`, PostgreSQL в Testcontainers, управляемые часы, sandbox-провайдер. Имя теста = ID требования + название сценария, например `BKG-03 Одновременная запись на последнее место`.
- Unit-тесты правил `core` также помечаются ID требований.
- Матрица трассировки строится поиском ID по коду и тестам.

## Risks / Trade-offs

- [Блокировка суммы на карте живёт у банков около 5–7 дней, а запись возможна почти за неделю] → неуспешное списание переводит запись в задолженность с оплатой по ссылке (PAY-05); если задолженностей много, стоит публиковать неделю не раньше чем за несколько дней.
- [Поток «Ожидает блокировки» на 10 мин занимает место, и им можно злоупотреблять] → короткий тайм-аут, не больше одной такой записи на спортсмена одновременно.
- [Вебхук провайдера может потеряться] → шаг сверки в D8.
- [Сервер в одном экземпляре: во время простоя проверка T−2,5 ч не выполнится вовремя] → после запуска задачи догоняют пропущенное; для MVP допустимо, требование «не позже 1 мин» действует при работающем сервере.
- [Токен в `localStorage` веб-клиента уязвим к XSS] → строгая CSP и отсутствие стороннего JS; переход на httpOnly cookie — после MVP.
- [Правило «приложение не делает возвратов» может противоречить законам о защите прав потребителей] → спецификации ограничивают только приложение; возвраты при необходимости клуб проводит вне него (PAY-10).
- [Опрос раз в 30 с увеличивает нагрузку] → для масштаба одного клуба несущественно.

## Migration Plan

Новая система, данных для переноса нет.
1. Локальное окружение: PostgreSQL в `docker-compose`, миграции Flyway применяются при старте сервера.
2. Первый администратор создаётся при старте из переменных окружения, если в системе нет ни одного администратора: регистрация выдаёт только роль «Спортсмен» (ACC-01).
3. Справочник типов (TRN-01) и цены по умолчанию заполняются миграцией.
4. Откат: остановить сервер и откатить миграции на пустую БД (данных до MVP нет).

## Open Questions

- Значения цен и способ их задания (по типу, по тренировке, абонементы) — меняется только источник цены по умолчанию (D7).
- Конкретный реальный платёжный провайдер для эксплуатации — добавится отдельной реализацией интерфейса.
- SMTP-провайдер для писем восстановления пароля и конкретное значение часового пояса клуба — задаются конфигурацией.
- Хостинг сервера и веб-клиента — решится на шаге развёртывания.
